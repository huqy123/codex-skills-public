# JVM 故障排查

先保留证据，再判断根因。没有日志、监控、线程或堆证据时，只能列可能性。

## 确认现场与采集风险

- 明确进程、故障开始时间、最近变更、流量、资源限额和受影响实例。
- 对照 CPU、内存、GC、线程数、连接池、请求及下游耗时，区分资源不足、应用缺陷和外部依赖变慢。
- JFR、堆转储和诊断工具的支持程度取决于 JDK、运行环境与权限；采集前核对工具、时长、停顿、磁盘空间和输出访问范围。
- 转储可能含密码、个人信息和业务数据，按敏感材料保管；不上传公开仓库或原样输出。

## 高 CPU

确认热点 Java 进程后，定位进程内耗 CPU 的操作系统线程，并对应到线程转储中的本地线程标识。间隔采集多份，避免单快照误判。

持续相同栈可指向循环、正则回溯或低效算法，仍需结合时间和采样确认；同时看 GC 消耗与容器 CPU 节流。栈变化并不自动表示正常，也可能是正常繁忙，需进一步证据区分。

## 卡死、死锁和线程上涨

- 比较多份转储的 `RUNNABLE`、`BLOCKED`、`WAITING` 和 `TIMED_WAITING`，线程状态本身不等于根因。
- 查看死锁报告；按锁、连接池、外部响应或队列分组等待者，寻找持有者与最慢依赖。
- 对照线程池与连接池上限，检查无限创建线程、阻塞任务、无界队列及未关闭执行器。

## 内存溢出

- 先区分堆、元空间、直接内存和无法创建本地线程；加大堆并非通用修复。
- 优先用已有故障转储，检查保留内存和到 GC Root 的引用路径；对象数量多不等于内存占用最大。
- 根据证据检查无限缓存、未清理上下文、监听器、一次加载大结果集、线程或资源泄漏。

## 验证结论

说明定位到的线程、对象和调用路径，列出证据与未排除项。在相近负载下确认延迟、CPU、线程和 GC 后内存恢复稳定；重启后恢复不等于根因已找到。
