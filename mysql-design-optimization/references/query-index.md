# 查询、索引与统计口径

## 性能证据

收集完整 SQL、多组典型参数、返回规模、实际结构和索引，以及慢日志中的次数、耗时、扫描量。使用当前版本支持的执行计划。

`EXPLAIN ANALYZE` 会实际执行查询，可能消耗显著资源；仅在已确认安全的语句和环境中使用。没有实测证据时只能提出待验证方向。

## 优化判断

1. 先看无用列、N+1、深分页、隐式转换、相关子查询和对索引列的计算，再看过滤、连接顺序、临时表、排序、回表及估算偏差。
2. 全表扫描或 `Using filesort` 不自动代表错误；小表或高返回比例可能合理。
3. 联合索引根据等值、范围、排序与返回列设计，结合选择性和完整工作负载验证，不把“等值列永远在前”当公式。
4. 检查左前缀复用、重复索引和 InnoDB 二级索引隐含的主键。宽主键会增加二级索引成本。
5. 新增索引说明写放大、空间、缓存、复制和 DDL 成本。删除前覆盖任务、导出及低频业务，不能凭短期零使用就判定无用。

使用相同 SQL 和多组代表参数比较计划、扫描量与耗时，同时核对结果及稳定排序不变，并观察写入和批量任务影响。

## 统计 SQL

- 先用一句话定义总体、时间事件、去重单位及指标。按项目、记录、订单或用户汇总时，明确是一条满足即可，还是全部满足；`MAX` 与 `MIN` 不能混用。
- 时间优先对应业务事件，使用明确时区与左闭右开区间。创建、更新、完成、审核时间不是同一个口径；可被覆盖的当前状态不能还原完整历史。
- 先圈定一批样本，再从同一批样本计算分子与分母；另一个独立样本需单列说明，不混算采用率或覆盖率。
- JOIN 前后检查是否一对多放大。关联靠业务主外键，不能仅凭同一个操作人或相同展示文字认定同一次事件。
- “设置过规则”“执行过计算”“得到正常结果”“最终采用”分别判断。告警是否合理属于业务定义；执行状态不能直接证明正确率，缺少计算记录也不能自动证明人工处理。
- 结果为空和分母为零时明确返回语义。粗略统计可以接受说明过的近似，不通过堆叠额外列或复杂 CTE 掩盖口径不确定。
