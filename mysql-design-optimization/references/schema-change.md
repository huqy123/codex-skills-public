# 结构变更与多环境发布

## 变更前

- 逐环境核对版本、结构、索引、行数/大小、历史空值和字符集，不假定测试、预发与生产一致。
- 明确相关服务、消息消费、任务和新旧版本是否并存，以及先发库还是先发代码。
- 按真实风险检查长事务、元数据锁、复制延迟和磁盘/临时空间。测试小表几秒完成不证明生产也一样。
- 需要备份时写清结构、数据与受影响对象及恢复要求，优先项目已有备份工具，不为几个已知表默认新造复杂备份框架。

## 执行与兼容

- 一次性已知变更优先直接 SQL；重跑、多环境差异或现有迁移规范确有要求时再增加判断与版本管理。
- 可行时采用扩展、迁移、收紧：先加兼容结构，发布兼容代码，分批回填核对，最后收紧约束或删除旧结构。
- 非空字段先核对历史业务值，必要时允许空并按主键范围分批回填，不用虚假默认值掩盖缺数据。
- DDL 算法和锁行为取决于精确版本、操作及表结构。需要限制重建风险时显式指定适用的 `ALGORITHM`/`LOCK`，先演练；不支持则停止分析，不静默降级。
- 在线 DDL 仍可能消耗 CPU、I/O、空间及等待元数据锁。DDL 通常隐式提交，普通事务回滚不能作为结构回退方案。

## 表重命名专项

检查实体映射、Mapper、运行时 SQL、定时任务、跨服务、导出、视图及存储对象。字段或 JSON 中若存有表名字符串，也要核对其含义，不能只全局替换代码。

明确是否需要暂停读写，以及库和代码如何同时切换。保留现有已执行迁移的历史记录，是否更新初始化脚本按项目规范判断，不要求历史环境重跑旧脚本。

## 回退与验收

- 分开设计应用回退、停止回填和结构恢复；删列、类型缩小和删除数据未必可逆，反向 DDL 也可能再次长时间锁表。
- 多环境脚本写清各段前提、执行顺序和次数。自动发布沿用项目现有迁移工具，不因表名相同直接复制执行。
- 上线后核对结构、约束、非法值、回填进度、业务读写、执行计划、慢查询、锁与复制；报告实际结果和未验证项，不只报 SQL 执行成功。
