# 发布候选审查

## 基本原则

- 先明确目标是提测、合并还是发布，并记录候选版本、目标引用和实际审查范围。
- 分开说明需求“应该怎样”、代码“实际怎样”和页面/数据/消息/日志“运行后怎样”。
- 编译通过只证明代码可编译，不能证明入口可达、数据不丢、批量范围正确或下游可用。
- 有阻断缺陷或关键证据缺失时，不给出放行结论；未授权不修改、提交、合并或推送。

## 候选范围

- 记录候选和目标提交SHA、目标引用是否本轮核实。审查从共同祖先到候选的改动，再补充属于本次交付的已暂存、未暂存和未跟踪文件。
- 工作区干净不等于没有候选改动。普通 `git diff` 不包含未跟踪文件，需查看其内容，说明排除项及理由。
- 提测可审查未提交的完整工作区，但说明构建包含什么；合并前拟交付文件应进入明确候选提交，上线前绑定不可变的待部署产物。
- 合并判断核对与指定目标版本的实际或只读模拟合并结果；只确认没有文本冲突不能证明兼容最新目标。

## 正向核对

沿“真实入口 → 输入与契约 → 权限和校验 → 处理 → 状态/副作用 → 可观察结果 → 下游”逐段核对：

- 输入、标识、空值和版本是否完整。
- 复制、覆盖、删除、批量和失败重试是否保持范围和状态一致。
- DTO、实体、JSON、数据库、消息和快照之间是否丢字段。
- 保存后重新查询、重开和下游消费是否读取同一份最新数据。
- 适用时检查数据库迁移、兼容、并发幂等、缓存、监控、回滚和容量。

涉及持久化时检查“写入 → 再查询或重开 → 再次使用”，不能只证明写入成功。新增字段逐段核对请求、DTO、实体、JSON、数据库、消息及消费者，分清 `null`、空字符串和字段缺失。

复制或覆盖时，按业务要求明确哪些字段复制、保留、重建、重置或禁止复制。ID、归属、版本、状态、地址和审核记录不能凭字段名直接决定。

## 必测场景

按改动选择：单条/批量、无数据/已有数据、首次/再次打开、成功/失败重试、新旧数据、复制/修改/删除、前端提交/绕过前端的非法请求。每个场景写明触发者、判断条件、状态变化、观察方式和下游结果。

## 分阶段判断

- 提测：本地必要检查已通过，无已知阻断；只能在测试环境验证的数据库、消息或外部接口列为明确待测项。探索性验证不写成已通过。
- 合并：完整候选范围固化，需求和兼容性已核实；项目要求的检查针对实际或等价的目标合并结果执行。
- 上线：关键链路有测试或类生产证据，适用的迁移、配置、部署顺序、监控和回退可执行。测试与部署使用同一产物，或有可验证且不重新构建的晋级链路。

不适用的维度按需说明理由；不把面向复杂发布的检查机械套到无关改动。关键链路、候选范围或产物一致性仍未知时，不给出正式上线通过结论。

## 反向复核与结论

从最终页面或下游结果反查数据来源，重点找不可达代码、批量范围过大、复制误删和只在单层存在的字段。最后说明候选范围、检查命令和结果，明确哪些已验证、哪些只能到测试环境验证、哪些仍阻断。改完代码后重新读取最终 diff 并重跑受影响检查。

第二遍用找错的视角复核，不沿用“已经正确”的假设。风险较高且具备合适授权与资源时，可由另一审查者独立复核；本人重读不能称为独立审查。
